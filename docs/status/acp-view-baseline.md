# ACP 会话加载与流式显示基线（改动前）

> 状态：已验证记录。总 Issue [#422](https://github.com/AMA-Link/Armadra/issues/422)（ACP 加载与内容展示优化），本文是 B0 批（[#423](https://github.com/AMA-Link/Armadra/issues/423)）的产物：后面各批改动前后各跑一遍，对着这里的数字比。
> 脚本：`tools/probes/acp-view-bench.mjs`；合成数据：`tools/probes/fixtures/acp-session-gen.mjs`；脚本化假 Agent：`tools/probes/fixtures/acp-bench-agent.mjs`；比对基线：`tools/probes/acp-view-bench-baseline.json`。

## 1. 场景

真 core（`apps/desktop/out/core/main.js`），临时数据目录与临时 HOME；Agent 是脚本化的假 Agent，会话内容是合成的，不用任何真实账号。

| 项               | 做什么                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 打开会话         | 预先放一份 300 回合的合成镜像（778 KiB，每回合约 1.6 KB 的 Markdown，每 3 回合一对工具调用与结果），起会话后读 `GET /api/acp/sessions/{id}/log?after=0`，连读 5 次     |
| 流式分块         | 假 Agent 以每秒 50 块、共 200 块、每块约 48 字符吐 `agent_message_chunk`，每块带 `⟦序号:毫秒时间戳⟧`；在工作空间事件流（控制面 `/api/ws`）上量到达延迟                 |
| 重连同步         | 断开事件流再连 5 次：连上的耗时，以及连上后页面做的那件事（整份重读 `…/log`）合计的耗时                                                                                |
| 转录解析         | 一份 20 MiB 的 Claude 形状转录：经 `GET /api/agent-status/{node}/transcript` 读 256 KiB 与 5 MiB（上限）两档；另给一份不经 core 的参照（整读逐行解析、尾读 256 KiB）   |
| 页面（`--page`） | Vite 开发服务器 + 无头 Chrome 打开同样的 300 回合会话：节点出现到最后一个回合画出来，以及随后 200 个分块各自从吐出到文字出现在 DOM 里的延迟，主线程 50 ms 以上的长任务 |

延迟都在同一台机器的回环上量，不含网络。页面一项用的是 Vite 开发服务器（未压缩的 React 开发构建），绝对值比打包版慢，用来对前后；不要拿它当用户体验的绝对数字。

## 2. 环境

Apple M1 Max，macOS 26.6，Node 26.10.0，Chrome 155（无头），基线 Armadra `main` `32546294`（v0.9.0），2026-10-20。

## 4. 怎么读

- **core 一侧不慢。** 打开 300 回合只要 8 ms 读文件加 1 ms 解析，重连后整份重读合计 12 ms，分块从 Agent 吐出到订阅者收到只要 2 ms。问题不在这里，而在每次都要读全量（731 KiB）：会话再长，这个数字线性增长（设计文档 §1.1 里 55 MB 的转录整读解析 153 ms）。
- **core 对每个分块做了两次同步写。** 每块 1 行镜像加 1.02 行 outbox，对应设计文档 §1.2 的 L3 与 L4。分块多的时候会把工作空间 5000 条保留额度挤满。
- **转录经 core 读 5 MiB（上限）要 84 ms，读 256 KiB 要 6.6 ms**，大致线性；参照的整读逐行解析 20 MiB 只要 40 ms，经 core 每字节的代价约是它的 8 倍（多出来的是归一化成条目再渲染成文本）。超过 5 MiB 的部分经 core 路径读不到，所以 20 MiB 的整读只出现在参照里。
- **页面才是瓶颈。** 打开 300 回合：节点出现到最后一个回合画出来要 2.1 s，其中一条 1.7 s 的长任务，主线程在这段时间完全卡死。流式时更糟：每个分块触发一次整体重渲，在 300 回合会话里每块约 1.2 s（开发构建），50 块每秒的速度根本跟不上——64 s 的窗口里只画出了约四分之一的分块，分块延迟 p50 达到 35 s，期间有 55 条 1.3 s 级的长任务。设计文档里「300 条助手消息每个分块约 340 ms」是只算 Markdown 重解析的下限，整页重渲的实际代价更高。
- 页面窗口内画出的分块占比受 64 s 窗口截断，是「在窗口内跟不跟得上」的度量，不是丢帧：其余分块仍在事件队列里。优化之后这个比例应当回到 1，分块延迟回到一帧级别。

## 5. 用法

```sh
pnpm libs:build
pnpm --filter @armadra/desktop build
node tools/probes/acp-view-bench.mjs [输出目录] [--turns 300] [--chunks 200] [--rate 50] \
  [--chunk-chars 48] [--runs 5] [--transcript-mib 20] [--page] \
  [--baseline 文件 | --no-baseline] [--write-baseline]
```

- 缺省只跑 core 一侧（几秒）；`--page` 另起 Vite 与无头 Chrome（需要 Chrome，`CHROME_PATH` 可指定），多花约两分钟。
- 产物：`<输出目录>/result.json`（`metrics` 是平铺的数字，`details` 带各项的分位数）与 `table.md`，缺省 `target/acp-view-bench/`。
- 与基线比对：读 `acp-view-bench-baseline.json` 里 `<平台>-<架构>` 那一份，任何一项比基线差 20% 以上并且超过该项绝对容差即失败；没有这台平台的基线时只报告。重录基线：连跑三次取中位数，改基线文件并同步本文。
- 所有进程都是探针自己起的，数据目录、HOME、工作目录都是临时的，跑完全部删除，只结束自己起的进程。
- 进 PR CI 的只有 `tools/probes/acp-view-bench.test.mjs`（参数、统计、比对规则、合成数据、假 Agent、输出形状，已并入 `pnpm release:test`）；真正的负载夜间跑，不进 PR CI。
